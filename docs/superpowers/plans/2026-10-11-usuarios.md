# Gestão de usuários — execução aprovada

Objetivo: aba Usuários exclusiva da conta proprietária de Christopher, com convite, classificação Engenheiro/Analista/Cliente e ativação/desativação. Não delegar a gestão ao classificar alguém como Engenheiro. Não permitir desativar a própria conta. Sem exclusão definitiva de contas.

- [ ] Migration adiciona gestor_usuarios fechado por padrão, invariantes da conta gestora e rotina administrativa transacional. Somente a conta proprietária confirmada recebe o indicador, por provisionamento administrativo separado.
- [ ] Função de servidor valida JWT, perfil ativo e indicador gestor_usuarios antes de listar e-mails, convidar ou alterar perfis. Chave administrativa só no ambiente da função, nunca no navegador. Convites usam URL configurada no Auth. Tratamento de erro não revela chaves/senhas.
- [ ] Telas passam por dados.js. Usuários lista nome, e-mail, categoria e situação; convite com confirmação explícita do destinatário/categoria; edição com confirmação de alteração/desativação e bloqueio durante envio. A categoria Engenheiro continua armazenada como Christopher. Usuário comum nunca administra mesmo se chamar API diretamente.
- [ ] Testes antes da implementação: gestor ausente/inativo/comum bloqueados; papel inválido recusado; promoção da própria gestão recusada; auto-desativação recusada; gestor autorizado altera terceiro. Dados fictícios em rollback e sem envio de e-mail nos testes.
- [ ] Integrar aba em desktop/celular, acessível mesmo sem obras. Atualizar snapshot, documentação e relatório. npm run check e revisão de segurança. Sem push/publicação do site.

Implementação nesta conversa, pelo agente. Publicar a função de servidor no Supabase faz parte da implementação aprovada; não publica o site nem envia o código ao GitHub. Envio real de convite ocorrerá somente por ação confirmada do gestor no app.

## Execução e decisões

- Usuário escolheu gerar links para compartilhar; não configurar SMTP nem enviar e-mails. Convites são link individual, com confirmação de destinatário/categoria; só divulgados após liberação do perfil.
- Migration aplicada; flag gestor provisionada somente na conta real proprietária. Teste SQL inicial falhou por função ausente e depois passou em rollback.
- Edge Function usuarios implantada com verify_jwt=true. Handler valida getUser, ativo e gestor_usuarios; RPC administrativo só service_role. Nenhuma chave administrativa no frontend.
- Testes de API cobrem sucesso de listar/alterar/convidar, identidade derivada do JWT e falha parcial sem divulgação de link; também comum/inativo/auto-desativação/entrada inválida/JWT inválido. Testes de dados cobrem respostas e erros. HTTP sem login contra função real retornou 401.
- Interface isolada: próprio usuário sem botões, cancelamento, desativação, reativação e confirmação de link fictício verificados. Fixture removida; nenhum convite real enviado/gerado no teste.
- Snapshot regenerado após coluna gestor_usuarios. Régua de lint inclui handler de servidor. Revisão independente não encontrou defeitos de autorização; ampliados testes de sucesso conforme observação.
- Proprietário confirmou que a aba abriu e mostrou sua conta no navegador real: listagem autenticada pela função implantada validada. Não foram gerados convites reais para terceiros pelo agente. APP_URL permanece local até etapa de publicação.
